# Интеграционные тесты

Запуск (нужен работающий Docker):

```sh
make integration-test
# Или напрямую:
go test ./internal/integration-test/... -v -tags=integration
```

Структура сценария:

```text
scenario/
  scenario_test.go
  scenario.yaml
  testcases/
    testcase1/
      request.json
      response.json
      init.yaml
      assert.yaml
```

`scenario.yaml` — таблица кейсов: имя для `t.Run`, описание и каталог.
Чтобы добавить кейс, создайте его каталог и добавьте запись в YAML.
При успехе ответ сравнивается с `response.json` в формате protobuf JSON.
Для ожидаемой ошибки добавьте в запись сценария поле `error`, например
`error: "operation failed"`. Тогда проверяются точное сообщение ошибки
без gRPC-кода и отсутствие ответа; файл `response.json` для такого кейса не нужен.
Состояние базы проверяется и при успехе, и при ожидаемой ошибке.

Контроллер собирается с настоящими service, repository и
pgxtransactor, как в `main`. Тест вызывает метод напрямую. Проверки сетевого
транспорта, interceptors и HTTP gateway в этот тест не входят.

Один контейнер PostgreSQL используется сценарием. Каждый кейс получает отдельную
базу с настоящими миграциями, которая удаляется после теста.

В `init.yaml` ключи — имена таблиц, значения — строки с колонками и данными.
`pg.NewDatabase(t, tc.Path("init.yaml"))` загружает файл через
`go-testfixtures.FilesMultiTables` и `Load` после применения миграций.
SQL в фикстурах писать не требуется. Для дат используйте UTC, например
`"2026-01-01T10:00:00Z"`.

`assert.yaml` имеет тот же формат. `db.Assert` вызывает `Dump` для всех таблиц
текущей схемы, кроме служебной `goose_db_version`, и сравнивает все их строки
и колонки. Порядок строк не учитывается;
лишние строки, отсутствующие строки и отличия значений приводят к ошибке.
Таблицы, отсутствующие в `assert.yaml`, должны быть пустыми: писать `booking: []`
необязательно. Для полностью пустой базы укажите `{}`. Неизвестное имя таблицы
в ожидаемом состоянии приводит к ошибке. Dump создаётся во временном каталоге теста,
ожидаемые файлы автоматически не перезаписываются.
JSON-объекты и массивы в текстовых колонках сравниваются по содержимому,
независимо от пробелов и порядка ключей.

Динамические `created_at` и `updated_at` можно не указывать в `assert.yaml`.
Если колонка времени не задана ни у одной ожидаемой строки таблицы, она
исключается из фактического состояния перед сравнением. Если задана — проверяется
как остальные колонки. Поэтому при создании пропускаются обе даты, а при
успешном обновлении — только `updated_at`; репозитории приложения не меняются.

`go-testfixtures` сбрасывает последовательности до 10000, поэтому первая
созданная запись в пустой таблице получает ID 10001.

Все Go-файлы тестов и вспомогательных пакетов имеют тег `integration`.
Обычный `go test ./...` не запускает контейнеры. Для проверки интеграционного
кода линтером используйте `golangci-lint run --build-tags=integration`.

Вспомогательные пакеты можно копировать между сервисами:

- `testdb`: `Start(t, "migrations")` запускает PostgreSQL,
  `pg.NewDatabase(t, tc.Path("init.yaml"))` создаёт отдельную базу с миграциями
  и начальным состоянием. `db.Pool` используется приложением,
  `db.Assert` проверяет фикстуры. Миграции и фикстуры используют один `sql.DB`.
  Подключения и база автоматически закрываются через `t.Cleanup`.
- `testcase`: `Load` читает сценарий, `tc.Path` находит файл внутри кейса,
  `tc.ReadRequest` читает protobuf JSON, `tc.AssertResponse(t, response, err)`
  проверяет ожидаемую ошибку или сравнивает ответ с `response.json`.

Пакеты не зависят от кода конкретного сервиса. Путь миграций задаётся относительно
корня проекта с `go.mod`, который находится автоматически из рабочего каталога теста.
SQL-файлы читаются с диска; Go-файл с `embed` в каталоге миграций не требуется.
В самом тесте остаются `t.Run`, сборка зависимостей и прямой вызов ручки.
